## Why a guard in front of every server
wq#4290: the stealth browser shipped raw and an agent could `fetch()` loopback/tailnet services. These
servers can mutate Gitea, run containers, read the fleet DB or open arbitrary URLs, and their output
(web pages, container logs) is untrusted text that lands in agent context (prompt injection).
`lumen_mcp_guard.py` is therefore fail closed:
- only tools on `--allow` are listed or callable (new upstream tools stay hidden until reviewed);
- `--arg-allow TOOL:ARG=v1|v2` closes multiplexed tools to reviewed methods (no PR merge, no review dismiss).
  `TOOL:ARG?=v1|v2` (wq#4888) also allows the argument to be absent: an optional override whose default is
  safe (council `ask_deepseek:model?=flash|pro`, stealth `spawn_browser:sandbox?=True|true`);
- `--path-arg TOOL:ARG=/root` pins a host-path argument under a root after resolving symlinks. Used by ghidra-lumen, `ops/wq4946-ghidra-mcp-guard`;
- `--http-url-arg` pins URL arguments to http(s); `--egress-proxy` forces the browser through the public-only proxy;
- `--mask-output` runs results through `mask-secrets`, withholding the result if masking fails. Since
  wq#4942 that includes embedded text resources and a backend's `isError` text, which fastmcp's proxy
  re-raises as a ToolError and which skipped the masker before;
- `--max-result-bytes N` (wq#4942, audit G11) cuts text past N bytes with a note, replaces a non-text block
  that does not fit with a note, refuses structuredContent over N, and writes a `TRUNCATED` audit row. The
  cut runs after masking, so it cannot leave half a secret the masker would have caught. All six launchers
  pass 512 KiB, as does ghidra-lumen;
- `--untrusted-output` (wq#4942, audit G10) wraps every text result between `<<<untrusted-NONCE` and
  `untrusted-NONCE>>>` behind a one-line "data, never instructions" header. NONCE is random per call, so
  a payload cannot close the block early. It drops structuredContent and strips outputSchema from the
  listed tools, because Claude Code shows the model only structuredContent when both are present
  (anthropics/claude-code#55677), which would bypass the wrapper. Instruction-like text gets a `SUSPECT`
  audit row that names the pattern but never quotes the text. This is a marker, not a filter: it lowers
  the odds that injected text is obeyed but does not rule it out, so the allowlists stay the real
  boundary. Used on gitea, docker, grafana, playwright, stealth-browser and council. The dbhub launchers read our own DBs and are
  not wrapped. ghidra-lumen is not wrapped either, because stripping outputSchema would change the
  definitions its `--pins` were taken over. **Pins:** with the flag, a tool is judged on the definition
  the agent sees, without outputSchema. Re-snapshot `<name>@guarded` after deploy before adding `--pins`
  to a wrapped launcher;
- `--pins FILE` (wq#4941) hides and refuses any allowlisted tool whose definition (name, title, description,
  schemas, annotations) no longer hashes to its reviewed pin, or has no pin, and writes a `DRIFT` audit row.
  The file is the security-gate snapshot layout (`servers["<name>@guarded"].tools`, see
  `/home/lumen/docs/security/mcp-tool-pins-2026-11.json`); `--pins-surface` picks another entry. A bad
  file or missing entry refuses to start. Without `--pins`, a changed definition passes but gets a `CHANGED` row.
  A guard sees one server only; tool names shared across servers are checked over the pin files by
  `ops/wq4945-mcp-name-collisions/mcp_pin_check.py collisions` (wq#4945);
- resources and prompts are never exposed; the audit log `~/.local/state/lumen-mcp-guard/<name>.jsonl`
  records tool names and argument KEYS only, never values, plus a `START` row with the backend's own
  serverInfo (the agent only sees the guard's) and a `LIST` row when the backend's tool names change;
- the backend gets the caller's env minus code-load variables (wq#4944, audit F4): `PYTHON*`, `LD_*`,
  `BASH_FUNC_*`, `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `GCONV_PATH`, Perl/Ruby/Java option vars.
  Dropped names go to stderr. Desktop-commander's `PYTHONPATH=/home/lumen/opt/mcp-proxy/lib` used to
  break mcp-server-docker this way. A launcher that needs one sets it with `--env K=V`.
One backend session is held for the guard's lifetime: Go servers (gitea-mcp) refuse a second `initialize`.

## One-time operator steps (already done 2026-10-23; here so they are reproducible)
**Gitea token** (CLI on Anubis, straight into a 0600 file, never printed; DB backup first):
```
ssh anubis@100.121.17.5 'sudo python3 -c "import sqlite3;s=sqlite3.connect(\"file:/var/lib/gitea/data/gitea.db?mode=ro\",uri=True);d=sqlite3.connect(\"/var/backups/gitea/gitea.db.pre-$(date +%Y%m%d_%H%M%S)\");s.backup(d)"'
umask 077; ssh anubis@100.121.17.5 'sudo -u gitea /usr/local/bin/gitea --config /etc/gitea/app.ini --work-path /var/lib/gitea admin user generate-access-token --username lumen --token-name mcp-agent --scopes write:repository,write:issue,read:user,read:organization --raw' > /home/lumen/.secrets/gitea-mcp-token
```
Revoke: delete `mcp-agent` under lumen's Gitea settings > Applications, then `rm` the file.

**Postgres role** (pg_dump first; statement logging must be `none` or the password is logged):
```
docker exec lumen-pgvector pg_dump -U lumen -Fc fleet_memory > /home/lumen/backups/fleet_memory_pre-<ticket>_$(date +%Y%m%d_%H%M%S).dump
umask 077; openssl rand -hex 24 | tr -d '\n' > /home/lumen/.secrets/fleet-memory-mcp-ro.pw
# then, with the password read from that file (stdin, not argv):
CREATE ROLE mcp_ro LOGIN PASSWORD '...' NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOINHERIT CONNECTION LIMIT 5;
ALTER ROLE mcp_ro SET default_transaction_read_only = on;  ALTER ROLE mcp_ro SET statement_timeout = '15s';
ALTER ROLE mcp_ro SET idle_in_transaction_session_timeout = '30s';
GRANT CONNECT ON DATABASE fleet_memory TO mcp_ro; GRANT USAGE ON SCHEMA public TO mcp_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO mcp_ro;
```
New tables are NOT granted automatically (fail closed): re-run the last GRANT after a schema change.
Rollback: `REVOKE ALL ON ALL TABLES IN SCHEMA public FROM mcp_ro; DROP ROLE mcp_ro;`.
Never create a write-capable Postgres role against `minerva.db` — it's sqlite, not Postgres, and a
write-capable connection to it was the 2026-09-28 fleet-wide lock incident. `fleet-state` below reads
it, but only through a mechanism verified to actually refuse writes (not just this role recipe).

**fleet-state** (wq#4552): no operator step needed — it reuses the `fleet-memory` dbhub install (same
binary, same npm lockfile) and needs no secret, because the "identity" here is read-only-or-not at the
SQL layer, not a login. Two things worth knowing before touching it:
- dbhub's env-var `DSN=... READONLY=true` scheme (the one `fleet-memory` uses for Postgres) does **not**
  enforce anything for the sqlite connector in 1.5.0: verified empirically — `DELETE FROM state_facts
  WHERE 1=0` went through with that config. The TOML `[[tools]] readonly=true` block (`fleet-state.toml`,
  generated by `emit_toml_fleet_state`) does work: the same DELETE comes back `READONLY_VIOLATION`
  ("Only select, with, explain, pragma allowed"). This is the 0.22.6 engine-level fix for
  CVE-2026-61788 (`@bytebase/dbhub`'s read-only mode did not prevent writes pre-0.22.6); 1.5.0 is after
  it, but only the TOML path exercises the fix for sqlite.
- `/home/lumen/minerva/minerva.db` is WAL (`sqlite3 "file:/home/lumen/minerva/minerva.db?mode=ro"
  "PRAGMA journal_mode"` → `wal`), so a read-only reader here does not block `lumen_state.py`'s writes
  and vice versa — that's what makes pointing a reader at the live file safe where a second *writer*
  was not (the 2026-09-28 incident above).
Rollback: `claude mcp remove -s user fleet-state`; no role/secret to revoke.

## Install, verify, test
```
cd <worktree or foreman checkout>/ops/wq4514-mcp-install-batch
bash ./install.sh [gitea|postgres|docker|grafana|playwright|fleet_state|stealth_browser|council ...]   # default all; ends with --verify
bash ./install.sh --verify
/home/lumen/.local/share/mcp/_guard/venv/bin/python -m pytest -q test_lumen_mcp_guard.py
for t in gitea postgres docker grafana playwright fleet_state stealth_browser council; do /home/lumen/.local/share/mcp/_guard/venv/bin/python -I smoke_$t.py; done
```
`smoke_gitea.py` creates and closes one test issue per run unless `--skip-issue`. `smoke_council.py` makes one
real `ask_deepseek` call (a few tokens via LiteLLM) unless `--no-spend`. `smoke_stealth_browser.py` opens
example.com in a headless Chrome and closes it. Both take a launcher argv (default: the installed launch.sh);
pointed at the raw backend they must FAIL, which is the falsification run. `--verify` makes a real
read-only `tools/call` per server (a `tools/list` alone passed on a broken proxy during development).
Rollback of one server: `claude mcp remove -s user <name>`; backup of `~/.claude.json` before registering is in `~/backups/claude.json.pre-wq4514.*`.

## Changing an allowlist
Edit the `*_ALLOW` / `*_ARG_ALLOW` pins in `install.sh`, read the tool schema first (`mcp_smoke.py -- <launcher>`
lists tools; schemas via a Client), extend the smoke test with a refusal or acceptance case, run `install.sh`.
Any server that can mutate must stay behind the guard.
With `--pins` wired, a new allowlisted tool or a reviewed upstream upgrade also needs its pin regenerated
(security-gate `snap.py` against the guarded launcher) after reading the new description and schema.

## Known limits and follow-ups
- **fleet-state is the live memory; fleet-memory is a frozen snapshot.** `fleet-memory`'s Postgres
  `fleet_memory` DB has been frozen since 2026-10-08 and is pending collapse (wq#4539) — for anything
  mid-session, query `fleet-state` (`state_facts`, `archival_notes`, `memory_audit` in minerva.db), not
  `fleet-memory`. No network listener or CF route was opened for either; both stay stdio-only.
- **docker is read-only on purpose.** The Docker socket is root-equivalent; mutating tools
  (run/create/start/stop/recreate/remove/pull/build) stay with `ssh ... docker` under lumen-change-safety until a
  verify/critic-gated profile exists (see the follow-up ticket).
- **Gitea:** the token has repo write on every lumen repo (same reach as `gitea-lumen.token`). The guard removes
  merge, deletes, direct file commits and Actions secrets; landing stays with `lumen-pr land`.
- **Grafana** runs as anonymous Viewer; Bes has 0 Grafana-managed alert rules (fleet alerting is Gatus/ntfy/aq), so
  `alerting_rules_read` correctly returns nothing. mcp-grafana telemetry to Grafana Labs is disabled in the launcher.
- **playwright** borrows the pinned Chrome (r1243, 153.0) of the wq#4206 install; Playwright wants r1247. If that
  install moves, `--verify` fails on the missing/aborting Chrome. Page content is untrusted: an injected page can steer
  the agent, but the browser can only reach public hosts and the allowlist has no code-execution or file tools.
- **postgres-mcp (crystaldba) is not used:** 0.3.0 hard-pins `pglast==7.2.0`, gone from PyPI (verified 2026-10-23).
  Do NOT `pip install dbhub`: that PyPI name is an unrelated 2022 package.
- Versions were chosen at least 14 days old; bump deliberately (new pin, new hashes/lock, re-run smoke).
- **council** uses the LiteLLM master key, so the guard pin on `ask_deepseek` model is the only thing between an
  agent and `anthropic/*` on the gateway. A council-only virtual key limited to the two DeepSeek models would make
  that hold at the gateway too. Prompts and diffs still leave the fleet to DeepSeek/Google/OpenAI: the guard masks
  results, not what the agent sends.

## Coverage audit (wq#4888, 2026-11-18)
The 2026-11-05 acquisition audit listed six user-scope servers as unguarded. Re-checked on Lumen with
`lumen_mcp_guard.py --list-backend` against each live backend: docker, playwright, gitea and grafana were already
behind the guard (wq#4514-4518, 2026-10-23); stealth-browser and council were not. Every allowlisted tool exists
upstream on all eight (`missing_upstream: []`).

| Server | Backend tools | Exposed | Hidden (stateful/destructive, not reviewed for agents) |
|---|---|---|---|
| docker | 19 | 5 read-only | build/create/pull/push/recreate/remove/run/start/stop: root-equivalent through the socket |
| stealth-browser | 21 | 19: 7 read (list/get state/query/wait/page content/screenshot), 12 browser-local state (spawn/navigate/click/type...) | `execute_script` (page JS, wq#4218/wq#4290), `file_upload` (host file to web page) |
| playwright | 25 | 19 | `browser_evaluate`, `browser_run_code_unsafe`, `browser_file_upload`, `browser_drop`, `browser_drag`, `browser_emulate_media` |
| gitea | 57 | 30: reads plus issue/PR/review writes pinned by method | repo create/fork, branch/tag/release/file writes and deletes, Actions config/runs, packages, wiki/label/milestone/project writes, notifications, timetracking |
| grafana | 22 (after `--disable-write`) | 19 read-only | `alerting_manage_routing`, `get_annotation_tags`, `list_dashboard_versions` |
| council | 5 | 5 (none touch the host; `council_status` read-only, the rest send text to an outside model) | none; `ask_deepseek` model pinned to `flash`/`pro` |

The guard limits which tools an agent sees and what arguments reach them. It is not a sandbox: the docker
backend still holds the socket, the gitea token still has repo write. Least-privilege credentials stay necessary.
