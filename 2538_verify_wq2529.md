## Contradiction: the lint only recognizes the literal token `grep`

`apply_wq_patch.py`'s `_liveness_grep_invert_line` (and the sweep's independent copy) gates
on `tok != "grep" and not tok.endswith("/grep")`. `egrep`, `fgrep`, `zgrep` (and `rgrep`,
`bzgrep`, `xzgrep`, `zegrep`/`zfgrep`) are none of those — they're separate binary names,
not `grep` invoked with a flag — so the scan skips their argument list entirely and the
exact always-true bug wq#1975 shipped with is filable again under a different name:

```
$ /home/lumen/bin/wq edit 2542 --detail "Liveness: egrep -v pattern file.txt"
edited 2542: detail        # NOT refused
$ /home/lumen/bin/wq edit 2542 --detail "Liveness: fgrep -v pattern file.txt"
edited 2542: detail        # NOT refused
$ /home/lumen/bin/wq edit 2542 --detail "Liveness: zgrep -v pattern file.txt.gz"
edited 2542: detail        # NOT refused
```

This is not hypothetical: a leftover ticket (2539, `probe-test-do-not-create-2`, detail
`Liveness: git show HEAD:doc | egrep -v needle`) from this same wq#2538's own prior
(killed) attempt was sitting in the live queue with status `blocked`, an unrefused
instance of exactly this bug shape. Deleted as cleanup during this pass — see below.

The README (`ops/wq2529-lint-liveness-grep-invert/README.md`) and the commit message both
describe the guard as catching "any grep invocation" with an invert flag; the implementation
is narrower than the claim. Since `egrep`/`fgrep`/`zgrep` are standard GNU/BSD utilities an
agent would reach for exactly as often as bare `grep` (extended regex, fixed-string, or
gzipped-log probes), this is a live gap in the class of bug the ticket exists to close, not
an exotic edge case.

Fix recommendation (not applied here — verify-only, per archetype 8): widen the binary match
in both `apply_wq_patch.py` and `sweep_liveness_grep_invert.py` to
`re.fullmatch(r'(.*/)?(z|b?z|x?z)?[ef]?grep', tok)` or an explicit allowlist
(`grep`,`egrep`,`fgrep`,`zgrep`,`zegrep`,`zfgrep`,`rgrep`,`bzgrep`,`xzgrep`), then re-run the
one-time sweep against the live queue.

## Secondary finding (non-blocking): false positive on dash-prefixed search patterns

`grep -q -e -version file.txt` (a legitimate, non-inverted probe using `-e`/`--` to search
literally for a pattern that itself starts with `-`) is refused — the scan flags any token
after `grep` that starts with `-` and contains `v`, which includes the *pattern* argument
when it happens to look like that. Confirmed live:

```
$ wq edit 2542 --detail "Liveness: grep -q -e -version file.txt"
REFUSED: wq#2529 — Liveness: line uses grep -v (inverted match) ...
```

No occurrence of this shape exists in the current live queue (checked), so it is not
blocking anything today, but it's an over-broad heuristic worth noting alongside the
under-broad one above.

## Attempts to break the fix that did NOT find a defect

- Multiple grep invocations on one `Liveness:` line, mixed with `|`/`;`/`&&`: the token
  scan correctly stops at each separator and re-anchors on the next `grep` token.
- `grep --invert-match=...`: not a real GNU grep form (`--invert-match` takes no argument),
  not a viable bypass.
- Editing unrelated fields (`wq edit <id> --pri 3`) without touching `--detail` does not
  re-trigger the lint — correct, no regression risk to unrelated edits.
- Aliasing via a variable (`$GREP -v`) would bypass, but this is not a realistic shape for
  a `Liveness:` probe stored as static ticket text (no shell expansion happens at rest) and
  is out of scope.
