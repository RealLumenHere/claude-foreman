## Non-blocking finding: the ledger's default path is *inside* the repo it claims to be outside of

`mask_replay.py:71-78`'s comment states the ledger "lives under foreman state (not this
repo) because it is runtime fact ... not code." But `ROTATED_LEDGER_PATH` defaults to
`os.path.join(FOREMAN_ROOT, "rotated_ledger.json")`, and `FOREMAN_ROOT` defaults to
`/home/lumen/foreman` — which **is** this repo's working tree (`git -C /home/lumen/foreman
rev-parse --show-toplevel` → `/home/lumen/foreman`). Confirmed live: the seeded file sits
untracked at the repo root (`git status --porcelain` → `?? rotated_ledger.json`), and
`git check-ignore -v rotated_ledger.json` exits 1 — no `.gitignore` rule covers it.

This repo has an established, explicit convention for exactly this situation — `.gitignore`
already lists `/state.json`, `/acceptance.json`, `/evidence.json`, `/events/`, `runtime/`,
etc., each with a comment explaining why it is runtime state and not source. `wq#2543`
added a new root-level runtime-state JSON file following that same pattern but did not add
the matching `.gitignore` line, so a future `git add -A` (against CLAUDE.md's own guidance,
but it happens) or any `git add .` in `/home/lumen/foreman` would stage it. The blast radius
is low — the file holds only hashes, timestamps and operator notes, never a value — but it
directly contradicts the code's own "not this repo" claim and is a one-line fix
(`/rotated_ledger.json` in `.gitignore`). Not applied here — verify-only, per archetype 8.

## Attempts to break the fix that did NOT find a defect

- Malformed ledger JSON (`"not json"`) and a missing path both live-probed through
  `load_rotated_ledger()` → `{}` in both cases, no exception, no false ROTATED verdicts.
- Double `record_rotated()` on the same hash with two different tickets → ledger keeps only
  the second write (live probe, not just the pytest case), so a re-confirmation cannot
  leave stale ticket attribution behind.
- Looked for any code path besides `main_record_rotated` that could write the ledger
  (auto-write on replay, a self-clearing burn, etc.) — none exists; `replay()` only calls
  `load_rotated_ledger()`.
- Checked whether `rotated=` being checked before `faithful=` in `report()`'s mark logic
  could let a re-cut *and* ledgered record hide something — no: `unaccounted()` filters on
  `rotated` independent of `faithful`, so the two conditions can't mask each other.
- Considered a sha256-12 truncation collision as a bypass vector — pre-existing 48-bit
  hash scheme from before this PR, not a new risk it introduces.
