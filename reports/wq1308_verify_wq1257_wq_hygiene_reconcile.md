## Verdict: CONTRADICT

`find_artifact()` (`wq-hygiene-reconcile:81-99`) returns on the **first** regex match —
`ARTIFACT_URL_RE.search(notes)` runs unconditionally before the sha-token scan, and
`.search()` is position-independent within the note text. It only ever inspects ONE
citation, never all of them.

This fleet's real notes routinely cite **multiple** artifacts together. Confirmed live
against `/home/lumen/agents/work-queue/queue.db`:

    "foreman PR#219 http://.../pulls/219 + lumen-bin PR#53 http://.../pulls/53 + kb 65a5c39"
    "... Decoupled from unlanded wq#1289 per ISSUE-LOG.md #105 ..."

Multi-citation notes that mix real completion evidence with incidental/context references
to OTHER (possibly still-open) PRs are the norm, not an edge case.

### Reproduction

Unit-level, no network/token dependency (`find_artifact` alone):

```
notes = "closed, landed as deadbeef000...; see also http://.../pulls/999 (unrelated follow-up, still open)"
find_artifact(notes) -> ("url", "http://.../pulls/999")   # sha never inspected
```
Confirmed independent of citation order (sha-first vs URL-first in the text — same
result either way, since `.search()` scans the whole string).

Full `rot_reason()` path, with `pr_merge_state`/`sha_landed` swapped for controlled
verdicts (avoids depending on a live reachable forge PR — the underlying regex/ordering
bug is what's under test, not network reachability):

```python
whr.pr_merge_state = lambda url: ("open", f"{url} is still OPEN")   # the unrelated PR really is open
whr.sha_landed     = lambda sha: ("/home/lumen/foreman", True)      # the real evidence really landed

notes = "closed, landed as deadbeef...; see also http://.../pulls/999 (unrelated follow-up, still open)"
rot_reason(notes) -> "evidence PR no longer shows merged: http://.../pulls/999 is still OPEN"
```

Result: a DONE ticket with genuinely-landed, verifiable sha evidence gets a **false rot
alarm** — `sweep_done` pages Frank via ntfy (`FLAG wq#N: flagged`) — purely because an
unrelated, merely-referenced still-open PR link sits in the same note and is matched
first. The real evidence is never inspected.

Symmetric, milder failure on the repair side (`sweep_open`/`repair_candidate`): a
genuinely-landed sha cited *after* an incidental PR/URL reference in an open ticket's
notes is silently never found, so a real done-but-open ticket is **not** auto-repaired.
False negative, safe direction, but it undermines the ticket's own stated purpose
("board says open, reality says done" repair).

None of the 6 shipped tests use a multi-artifact note — every fixture cites exactly one
sha or one PR URL — so this gap was never exercised.

## Severity

Directly contradicts the ticket's own design intent: "if it no longer checks out, don't
guess — FLAG to FRANK... transition-based... alert-storm rule." The gap is not about
repeat-alerting; it's a false positive from ambiguous artifact selection, generated by
the fleet's own dominant note-writing style. Every DONE ticket in the 14-day lookback
window whose notes cite more than one artifact — a common pattern per the two live
examples above — is one incidental unrelated-PR-reference away from a spurious high-
priority ntfy page.

## Fix shape (not applied — verify-pass is not a re-implementation gate)

`find_artifact()` should collect every citation in the notes (all URL matches + all
sha-shaped tokens + all existing paths) and `repair_candidate()`/`rot_reason()` should
require ALL cited artifacts to verify (or at minimum keep scanning past a
non-matching/irrelevant kind instead of committing to the first regex hit), rather than
stopping at whichever pattern happens to match first.
