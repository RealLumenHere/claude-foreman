wq#2751's diagnosis and fix are technically sound. No defect found in the mechanism itself.

## What was checked

**Mechanism review (cold read against the actual installed source, not just the README's
claims):** `loopback-listen.cjs` monkey-patches `net.Server.prototype.listen`, rewriting a
matching-port `listen()` call to bind `127.0.0.1`. Traced all four call shapes it handles
(`listen(port)`, `listen(port, cb)`, `listen(port, host)`, `listen({port})`) against supergateway
3.4.3's actual call site (`app.listen(port, () => {...})` in `stdioToStatelessStreamableHttp.js`
and siblings) -- confirmed the exact shape used is one the patch correctly rewrites, verified by
hand-tracing the argument splicing, not just trusting the bundle's own claim. `NODE_OPTIONS`
propagation confirmed correct: supergateway is `#!/usr/bin/env node`, and the drop-in sets the
env on the ExecStart process itself (supergateway), which is the process that opens the TCP
listener -- the spawned stdio child never listens on a socket, so env-inheritance into the child
is irrelevant to this fix.

**Bundle's own test suite:** `python3 test_wq2751.py` -- 23/23 pass (isolated harness, spins up
real supergateway + projects_app instances with fixtures). `--live` (checks the actual running
systemd services on this box) -- 4/6 pass: the 2 expected FAILs are chrome-mcp/memory-mcp still
bound wide (control-plane half genuinely not deployed yet, matching the README); the 4 PASSes
confirm the projects-app half (traversal fix + loopback bind) is live and correct.

**Deployed-state cross-check:** `/home/lumen/projects_app.py` is byte-identical to the bundle's
shipped copy (`cmp`), backup present (`projects_app.py.bak.20260926_wq2751`), service active
since `2026-09-26 03:19:25Z`. The unattended half of this PR is genuinely live, not just staged.

**Contract compliance (this ticket's explicit requirement):** the bundle had no `--verify`
handler, and `ops-deploy-drift` hardcodes looking for a file literally named `install.sh` -- a
`--verify` arm bolted onto the existing `apply.sh` would never be discovered by the automatic
sweep. Added `ops/wq2751-listener-audit/install.sh` (this PR: claude-foreman PR#1143, commit
`3dd7effcb9`) implementing only the `--verify` branch per `ops/VERIFY_CONTRACT.md`, deferring all
actual deploy/rollback logic to the existing `apply.sh` (one source of truth). Checked both
halves; added a direct `ss`-based socket-bind check for the control-plane half since the
file+unit-presence helpers alone can't prove the process actually bound to loopback. Ran it
against live state: exits 1 with 5 `MISS` lines, all correctly under the not-yet-deployed
control-plane half -- matches reality exactly.

request) as of its audit window (2026-09-26 00:36-02:00Z). That is no longer true: someone
reinstalled `@modelcontextprotocol/server-memory` at `05:33Z` today and the service has been
stable since (39+ min uptime at check time, no journal entries, successful `initialize`
handshake logged). Confirmed live: `initialize` POST from Thor's tailscale IP to `100.117.66.102:3104`
returns HTTP 200 -- the anonymous create/delete_entities write-surface the original audit flagged

during the original audit. This doesn't change what to do (the fix is the same loopback bind,
already staged, still correctly gated to Frank per CONTROL-PLANE RULE 3) -- it changes how soon it
matters. Paged directly (`ntfy-send -t lumen-alerts`) rather than left for this report alone to
surface, since the exposure window is materially worse now than when wq#2751 closed.

## Outstanding (not this ticket's job, flagging for the record)
`ops-deploy-drift`'s `install.sh`-only filename assumption is itself a small class-level gap --
any bundle using a differently-named multi-verb script (like this one's `apply.sh`) silently never
gets real verification, falling back to heuristic-only forever. Not filing a separate ticket for
this alone; noting it here in case a future audit of `ops/wq*/` bundles wants to check for the
same pattern.
