## Proposed Change

Retire `dispatch-deadman.service`/`.timer` — do not restore the missing script.
Restoring it would resurrect a redundant, inferior (ad hoc, pre-wq#825) mechanism
alongside the one that's already designed, tested, and actively alerting.

**Step 0 — precondition check (must pass before deleting anything):**
```bash
systemctl is-enabled lumen-foreman-selfheal.timer   # expect: enabled
systemctl is-active  lumen-foreman-selfheal.timer   # expect: active
python3 /home/lumen/foreman/dispatcher/dispatcher_health.py status
```
If either `is-enabled`/`is-active` check fails, STOP — do not proceed to Step 2. That
would mean the health_state.json evidence above was written by the *other* mechanism
(`dispatch_health.py` via `lumen-foreman-health.timer`) instead, or coverage has since
lapsed; re-diagnose which timer is actually live before removing the old alarm.

**Step 1 — snapshot the current units for rollback:**
```bash
systemctl cat dispatch-deadman.service dispatch-deadman.timer \
  > /home/lumen/foreman/plans/wq997-dispatch-deadman.unit.bak 2>&1
systemctl show -p FragmentPath dispatch-deadman.service dispatch-deadman.timer
```

**Step 2 — retire the units:**
```bash
sudo systemctl disable --now dispatch-deadman.timer
sudo systemctl stop dispatch-deadman.service
sudo systemctl reset-failed dispatch-deadman.service dispatch-deadman.timer
sudo rm -f /etc/systemd/system/dispatch-deadman.service \
           /etc/systemd/system/dispatch-deadman.timer
find /etc/systemd/system -lname '*dispatch-deadman*' -print -delete
sudo systemctl daemon-reload
```
(Adjust the `rm` paths if Step 1's `FragmentPath` output points elsewhere, e.g.
`/usr/lib/systemd/system/` or a user unit dir.)

## Rollback Command

```bash
sudo cp /home/lumen/foreman/plans/wq997-dispatch-deadman.unit.bak-service \
        /etc/systemd/system/dispatch-deadman.service   # split from the .bak snapshot
sudo cp /home/lumen/foreman/plans/wq997-dispatch-deadman.unit.bak-timer \
        /etc/systemd/system/dispatch-deadman.timer
sudo systemctl daemon-reload
sudo systemctl enable --now dispatch-deadman.timer
```
Note: this restores the unit as it was — still pointed at a missing script, still
failing 203/EXEC every 10 minutes. Rollback undoes *our change* (unit removal), it does
not un-break the pre-existing bug; that's expected, since the bug is the reason this
ticket exists.

## Risk Assessment

- **Blast radius:** two small systemd unit files on one host, plus their systemd
  registration state. No application code, no running dispatcher/worker process, no
  data is touched.
- **What could go wrong:** the only real risk is retiring the alarm while believing
  coverage is live when it isn't — i.e. skipping Step 0 or having it pass on stale
  evidence. That would silently re-create exactly the incident-2 class this ticket
  exists to prevent (a dead watcher nobody notices). Step 0's live `is-active` check
  plus a direct `dispatcher_health.py status` call (not just the historical timestamp
  in `health_state.json`) is the mitigation — both must be checked at apply time, not
  inferred from this diagnosis pass's repo-only evidence.
- **Why acceptable:** `dispatch-deadman.service` currently does nothing but fail and
  spam the journal every 10 minutes — it has provided zero actual coverage since at
  least wq#942's discovery (2026-08-27) and, given it was superseded by wq#825 back on
  2026-08-23, likely far longer. Removing it changes no runtime behavior other than
  silencing a false-comfort failure; the real detection logic
  (`dispatcher_health.check_dispatcher_health()` inside `self_heal.py`) is unaffected by
  anything in Step 2.
- **Rejected alternative:** restoring `/home/lumen/bin/dispatch-deadman.sh` — this was
  the ticket's other listed option, but it would resurrect a mechanism the fleet's own
  history (wq#825, same day, two commits, ~12h apart) already replaced with something
  better-designed and already proven live. Doing so would add duplicate alerting for no
  benefit.
