# wq#1880 — probe-dead-references CRITICAL x3 (aq#1200): false positive in tbl_sweep2.py

## Current State

The alert (aq#1200 / probe-dead-references, wq#126) flags `lumen_dream_digest.py` for
referencing tables `note_merges` (lines 2, 89) and `prose_demotions` (lines 2, 97) that
the runbook tool, `/home/lumen/audits/tools/tbl_sweep2.py`, says are MISSING from
`queue.db`. (The ticket text shows the path as
`/home/lumen/research/minerva-ref/lumen_dream_digest.py` — that's the sweep-gated mirror
path substituted in for worker readability per the wq#1880 UNBLOCK note; the probe itself
scans the live file under `/home/lumen/minerva`, which is byte-identical per the hourly
sync guarantee, so the mirror copy is a faithful stand-in for diagnosis.)

**This is a false positive, not a real dangling reference.** Root cause is in the checker
tool, not the checked code:

- `/home/lumen/audits/tools/tbl_sweep2.py` extracts every `*.db` path *literal* from a
  scanned file via regex (`db_pat`), resolves each to a real file, unions the table sets
  of every DB it manages to resolve for that file, then flags any SQL table name found in
  the file's string literals that isn't in that union. It has no per-connection scoping —
  it checks every table reference in a file against every DB the file happens to mention.
- In `lumen_dream_digest.py`: `DB = os.getenv('MINERVA_DB', f'{MINERVA}/minerva.db')`
  (line 39) builds the path with an f-string. `db_pat` requires the literal to start
  immediately after an opening quote (or `file:`), so an interpolated `{MINERVA}` prefix
  never matches — this DB path is silently invisible to the tool.
  `QUEUE_DB = os.getenv('DREAM_QUEUE_DB', '/home/lumen/agents/work-queue/queue.db')`
  (line 41) *is* a plain literal and resolves fine.
- Because only `queue.db` resolves for this file, every table reference in it —
  including `note_merges` and `prose_demotions`, which the code only ever queries via
  `_absorbed()`/`_demoted()` against `DB`/`MINERVA_DB` (never `QUEUE_DB`) — gets checked
  against `queue.db`'s schema instead. Confirmed queue.db's actual tables (read directly,
  it's inside an allowed working directory):
  `agent_activity, agent_sessions, retired_sessions, slocks, slocks_ro, sqlite_sequence,
  tasks`. No `note_merges`/`prose_demotions` there — correctly so, they don't belong to
  this DB.
- `note_merges` and `prose_demotions` are real, actively-used tables in `minerva.db`, not
  phantom references:
  - `/home/lumen/research/minerva-ref/lumen_dream.py:206-233` `apply_merge_plan()` does
    `INSERT OR IGNORE INTO note_merges(absorbed_id,keep_id,sim,method,ts) VALUES (...)`
    against `DB = '/home/lumen/minerva/minerva.db'`, plus a chain-repair `UPDATE
    note_merges SET keep_id = ...`.
  - `/home/lumen/research/minerva-ref/lumen_prose_lifecycle.py:301-370` `apply_plan()`
    does `INSERT INTO prose_demotions(section_id,title,demoted_at,...) VALUES (...)`
    against `DB = os.environ.get('MINERVA_DB', '/home/lumen/minerva/minerva.db')`, and
    `restore()`/`stats()` `SELECT ... FROM prose_demotions`.
  - `lumen_dream_digest.py`'s own module docstring (line 9) states current row counts as
    of wq#1638: "note_merges at 5 rows, prose_demotions at 0" — not something you'd write
    about tables that don't exist.
  - I did not query `minerva.db` directly to double-confirm this — the live minerva root
    is unreadable to workers (wq#1467, credential surface) and `minerva-ref-sync`
    explicitly excludes `*.db*` from the mirror. The three independent code-path citations
    above are conclusive without it, and routing around that read boundary isn't
    appropriate here.
- This is the *exact* failure class `tbl_sweep2.py` already documents in its own comment
  (lines 11-15): "without this the path never resolves, tbl_sweep2 silently falls back to
  unrelated .db candidates found elsewhere in the same file, and flags a real table as a
  false MISSING" — which describes a previously-fixed instance for `daily_briefing.py`'s
  `queue.db` `'tasks'` table (fixed by tolerating the `file:...?mode=ro` URI idiom in
  `db_pat`). This ticket is the same failure mode, different trigger: an f-string-built
  path instead of a URI-mode connection string.
- Verified the regex behavior directly (against a local test snippet, not the live file):
  the current `db_pat` matches only the `queue.db` literal in this file; a version that
  also anchors on `}` (an f-string interpolation boundary) additionally captures
  `/minerva.db` from the `f'{MINERVA}/minerva.db'` expression.

## Proposed Change

Fix `db_pat` in `/home/lumen/audits/tools/tbl_sweep2.py` (line 16) to also resolve a `.db`
path literal that starts right after an f-string substitution's closing `}`, not only
right after an opening quote. This lets the tool's existing candidate-resolution fallback
(`os.path.join(os.path.dirname(f), os.path.basename(d))`, which already checks
`<scanned-file's-dir>/<basename>` — i.e. `/home/lumen/minerva/minerva.db` for a file
scanned out of `/home/lumen/minerva`) pick up `minerva.db` too, so `note_merges` and
`prose_demotions` get checked against the union of `queue.db` + `minerva.db` tables
instead of `queue.db` alone.

Diff:
```diff
--- a/tools/tbl_sweep2.py
+++ b/tools/tbl_sweep2.py
@@
-db_pat = re.compile(r'["\'](?:file:)?((?:/[^"\'?]*)?[a-zA-Z0-9_./-]*\.db)(?:\?[^"\']*)?["\']')
+db_pat = re.compile(r'(?:["\']|\})(?:file:)?((?:/[^"\'?]*)?[a-zA-Z0-9_./-]*\.db)(?:\?[^"\']*)?["\']')
```

(One-character change: the opening anchor group `["\']` becomes `(?:["\']|\})`. No other
line changes — `tbl_sweep2.py` isn't in a git repo, same as `sentinel_probes.py`, so this
ships as a foreman-repo-tracked diff for review plus a live in-place edit, matching the
`wq#1100`/`sentinel_probes.py` convention already used for other non-git live tools.)

Ship as `foreman/ops/wq1880-tblsweep-fstring-db/tbl_sweep2.diff` (the diff above) +

## Risk Assessment

- `tbl_sweep2.py` is a read-only audit script (opens every DB it resolves via
  `sqlite3.connect(f"file:{path}?mode=ro", uri=True)`) invoked on its own cadence by the
  `probe-dead-references` runbook — it mutates nothing, restarts nothing, and this change
  doesn't alter that.
- Blast radius of the regex change: it can only add newly-resolved DBs for files where a
  `.db` path literal happens to appear immediately after a `}` (an f-string substitution
  boundary) followed by a valid-looking db path and a closing quote — a narrow, specific
  syntactic shape. Worst case if it over-resolves somewhere else in `SCAN_DIRS`
  (`/home/lumen/agent`, `/home/lumen/minerva`, `/home/lumen/messenger`,
  `/home/lumen/dashboard`): a real MISSING-table finding for some *other* file gets
  masked by an incorrectly-unioned DB's coincidentally-matching table name (false
  negative). That's a strictly quieter failure mode than today's false CRITICAL, and I
  didn't find any other f-string-constructed `.db` path in the files I read while
  investigating this ticket. I did not exhaustively re-scan all four `SCAN_DIRS` for other
  f-string DB paths that this loosened regex might newly (mis)resolve — that's the one gap
  in this risk assessment worth a spot-check right after applying (see Verify).
- Acceptable: the fix is a single-character regex change to a non-production, read-only
  diagnostic tool, with a timestamped backup and one-line rollback.
