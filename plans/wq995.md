# wq#995: lumen-pokemon-live crash-looping: exit 1 every ~110s, frontier.json frozen 4 days

## Current State

Root cause found and confirmed live, with certainty — not a code bug, a systemd unit
conflict between two services that both try to bind the same port.

- `lumen-pokemon-live.service` (`ExecStart=/usr/bin/npx tsx src/live_agent.ts`,
  `Restart=on-failure`, `RestartSec=5`) needs to bind port 8871 for its
  `StreamServer` (`src/live_agent.ts:46` → `src/live.ts:15` → `src/stream.ts:276`).
- Port 8871 is permanently held by a **second, legitimate systemd service**:
  `lumen-kiosk-idle.service` (`/etc/systemd/system/lumen-kiosk-idle.service`):
  ```
  [Unit]
  Description=LPP Kiosk Idle Page (serves /home/lumen/pokemon/assets on :8871)
  After=network.target
  [Service]
  Type=simple
  User=lumen
  WorkingDirectory=/home/lumen/pokemon/assets
  ExecStart=/usr/bin/python3 -m http.server 8871 --bind 0.0.0.0
  Restart=always
  RestartSec=10
  [Install]
  WantedBy=multi-user.target
  ```
  Confirmed via `ss -ltnp`: `LISTEN 0.0.0.0:8871 users:(("python3",pid=2570408))`.
  `systemctl show lumen-kiosk-idle -p ExecMainPID,ExecMainStartTimestamp,NRestarts` →
  `ExecMainPID=2570408`, started `2026-08-23 16:21:13 UTC`, `NRestarts=1` — it grabbed
  the port once and has held it continuously ever since.
- **Neither unit has a `Conflicts=`/ordering directive against the other.** Both are
  `WantedBy=multi-user.target`; whichever starts first wins the port permanently.
  kiosk-idle happened to grab it on 2026-08-23 16:21:13 UTC and, because
  `Restart=always`, will never voluntarily give it up.
- `src/stream.ts:372-399` already has EADDRINUSE retry-with-backoff logic added for
  `wq#860` (comment literally names "a debug http.server left running" as the
  anticipated cause: 712 restarts / 1h40m outage). It retries 12x with backoff up to
  15s (~90s total), then `console.error("[stream] FATAL...")` + `process.exit(1)` by
  design, so systemd's restart loop can fire rather than hang forever. This is working
  exactly as designed for a *transient* squatter — the actual defect is that
  kiosk-idle is not transient, so every single restart cycle exhausts all 12 retries
  and dies. Confirmed live in the journal just now (11:41:27–11:42:29 today), full
  12-retry sequence reproduced verbatim, ending in FATAL + exit 1.
- `systemctl show lumen-pokemon-live -p NRestarts` → 425 and climbing, restart every
  ~110-115s (matches ticket). `ActiveState=active`/`SubState=running` per systemd
  (Restart=on-failure keeps it "running" between crashes — this is why the unit
  doesn't show as failed).
- `/home/lumen/pokemon/runtime/frontier.json` mtime = `2026-08-23 13:22:40 UTC` —
  ~3 hours *before* kiosk-idle grabbed the port (16:21:13). Consistent timeline: the
  live agent was working, then at some point stopped/restarted; from 16:21:13 onward
  it could never rebind and has never gotten past stream-server init to resume writing
  frontier.json since. 4 continuous days of crash-loop, zero forward progress.
- journalctl only retains data back to today 08:21:10 UTC (single boot recorded,
  `journalctl --list-boots` shows only boot idx 0 starting today — journal storage is
  volume-limited/rotated on this host), so the historical 4-day crash-loop can't be
  directly journal-grepped past that point, but the still-running squatter PID's own
  `ExecMainStartTimestamp` (2026-08-23 16:21:13) is independent, harder evidence and
  lines up with the ticket's reported freeze time.

## Proposed Change

Two-part fix: unblock the current crash loop now, then make the two units mutually
exclusive so this can't recur.

**1. Immediate unblock** — stop the process currently squatting the port:
```
systemctl stop lumen-kiosk-idle.service
```
`lumen-pokemon-live`'s own `Restart=on-failure`/`RestartSec=5` will bring it back
within 5s and it will bind 8871 immediately (no retries needed) since nothing else is contending
for it after this point.

**2. Durable fix** — make the units conflict so this can never recur regardless of
start order after a reboot or redeploy. Per `systemd.unit(5)`'s documented pattern for
two units contending over an exclusive resource ("it is best to add `Conflicts=` and
`Before=` to the unit that shall be stopped, pointing at the unit that shall be
started"), back up then edit `/etc/systemd/system/lumen-kiosk-idle.service`:
```
cp /etc/systemd/system/lumen-kiosk-idle.service /etc/systemd/system/lumen-kiosk-idle.service.orig-wq995
```
Add to its `[Unit]` section:
```
Conflicts=lumen-pokemon-live.service
Before=lumen-pokemon-live.service
```
(i.e. final `[Unit]` block: `Description=...`, `After=network.target`,
`Conflicts=lumen-pokemon-live.service`, `Before=lumen-pokemon-live.service`)

Then:
```
systemctl daemon-reload
```
`daemon-reload` only reloads unit definitions — it does not restart or stop anything by
itself, so this is safe to run immediately even while both units are live. Going
forward, any start (or restart-on-failure) of `lumen-pokemon-live.service` will cause
systemd to stop `lumen-kiosk-idle.service` first (ordering guaranteed by `Before=`),
so they can never both hold/contend for 8871 again.

Note: this fix does not wire up the reverse direction (auto-starting kiosk-idle's BRB
splash when pokemon-live cleanly stops) — that hand-off doesn't appear to have existed
before this incident either (kiosk-idle simply won the race and stayed up
indefinitely), so this fix doesn't regress anything that was working; it's a candidate
follow-up ticket, not part of this fix.

## Rollback Command

Step 1 rollback (rarely needed — step 2 supersedes it):
```
systemctl start lumen-kiosk-idle.service
```

Step 2 rollback:
```
cp /etc/systemd/system/lumen-kiosk-idle.service.orig-wq995 /etc/systemd/system/lumen-kiosk-idle.service
systemctl daemon-reload
```

## Risk Assessment

- Blast radius is contained to the two pokemon-live-stream units; neither touches
  Thor, Vault, cloudflared, or any Commander-path service.
- Stopping kiosk-idle right now removes the BRB splash for kiosk viewers only during
  the handoff window — but live is already crash-looping, so kiosk viewers are
  currently seeing whichever of the two half-broken states wins each ~115s cycle
  anyway. This fix strictly improves what they see (a working live stream instead of
  a frozen one), no regression.
- `daemon-reload` is inert by itself (reloads unit files only, doesn't stop/start
  units), so applying step 2 carries no risk even if step 1 hasn't been done yet.
- Adding `Conflicts=`/`Before=` is the standard, well-documented systemd idiom for
  this exact "two services fight over one exclusive resource" shape — low risk,
  fully reversible via the saved `.orig-wq995` backup.
- Residual risk: if `lumen-kiosk-idle.service` serves a purpose I'm not aware of
  beyond "BRB splash when live is down" (e.g. some other consumer depends on 8871
  always being reachable), permanently ceding the port to `lumen-pokemon-live` could
  regress that — I found no such consumer (no repo-tracked references, no other unit
  files, no crontab/timer referencing 8871 or kiosk-idle), so I judge this risk low,
  but flagging it since I couldn't fully rule out an undocumented external consumer.
