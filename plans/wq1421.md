## Proposed Change

**No dispatcher/config/service change** — the dispatcher is healthy; there's nothing
to fix in it. Per standing doctrine ("if the condition has cleared, mark the ticket
done and exit"), the acceptance criterion is already met (`spawned>0` on the latest
several passes).

The one loose end this diagnosis surfaced is the stale `alerts.db` row. The ticket
text says "`dispatch_recover.py`'s own `reset()` resolves aq#794 the moment a healthy
pass lands — do not resolve it by hand" — but that mechanism is not deployed (see
above), so nothing will ever call it for *this* incident; aq#794 will sit open
indefinitely (re-alerting/re-escalating on the same stale count) unless something
else closes it. Recommended action for the apply phase, in priority order:

1. Manually resolve `alerts.db` row 794 now that the condition is independently
   confirmed cleared, so it stops re-escalating on stale state:
   ```

   ```
2. Separately (not this ticket's job to execute, just flagging): land wq#1410 so
   future incidents get real auto-recovery + auto-resolve, and note in

## Risk Assessment

Minimal. This is a single-row UPDATE on a local sqlite alerts DB, not a production
service restart, config edit, or secret rotation — despite the ticket's [fleet-fires]
label, the actual proposed change has no blast radius beyond the alert-queue's
bookkeeping. Worst case: the row is marked resolved and a genuinely new stall
recurs later — `dispatch_health.py` still fires fresh `DISPATCHER STALLED` pages
independent of this row's status, so a real recurrence would not be silenced by this
change, it would just start a new count from a clean row (which is the intended
per-incident behavior wq#1410 is building anyway). The larger risk is *not* resolving
it: the row stays open, `aq_escalate.py` may re-fire another fleet-fires ticket on
the same stale 145-count/14:40Z timestamp, burning another diagnosis cycle on a fire
that's already out.
