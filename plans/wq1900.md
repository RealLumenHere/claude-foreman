## Proposed Change

This diagnosis session cannot get an exact number for the root-owned container
storage (needs `sudo`/root, which this headless read-only phase does not have
approved). The apply phase should run as a sequence — quantify first, then act
only on what the numbers show, rather than guessing at a fix that might not
free enough:

**Step 1 — quantify (read-only, safe, needs root):**
```
sudo docker system df -v
sudo du -xhs /var/lib/docker /var/lib/containerd
```

**Step 2a — if container storage (dangling images / stopped containers / build
cache) is a material chunk of the ~104G gap** (expected, given zero prune
automation has ever run here):
```
sudo docker system prune -af --volumes=false
```
`--volumes=false` (the default) never touches named volumes — only unreferenced
image layers, stopped containers, unused networks, and build cache are reclaimed;
no running container or its data is affected. Then add a weekly prune timer
mirroring the existing `lumen-backup-prune.timer` pattern (new unit
`lumen-docker-prune.timer`/`.service`, `ExecStart=/usr/bin/docker system prune -af --volumes=false`,
`OnCalendar=Sun 05:00`, offset from the backup timers) so this doesn't silently
re-accumulate — this is the durable root-cause fix the ticket asks for, not a re-ack.

**Step 2b — regardless of (2a)'s yield, tighten `REPO_LOCAL`'s retention** since
today's successful prune still left root critical under the current policy.
Edit `/home/lumen/services/backup/scripts/backup-prune.sh` line 30
(`--keep-hourly 24 --keep-daily 7 --keep-weekly 4 --keep-monthly 6`) to
`--keep-hourly 12 --keep-daily 7 --keep-weekly 4 --keep-monthly 6` for both
`CLASS` values, matching what `backup-critical.sh`'s hourly-critical cadence
actually needs for recovery (12h of hourly granularity, falling back to daily
beyond that — Frank should confirm this RPO is acceptable before it's applied).
Then run once immediately to reclaim now rather than waiting for next Sunday:
```
RESTIC_PASSWORD_FILE=/home/lumen/services/backup/.restic-password \
RESTIC_CACHE_DIR=/scratch/restic-cache \
/home/lumen/.local/bin/restic -r /home/lumen/backups/local --retry-lock 50m forget \
  --tag critical --group-by host --keep-hourly 12 --keep-daily 7 --keep-weekly 4 --keep-monthly 6
/home/lumen/.local/bin/restic -r /home/lumen/backups/local --retry-lock 50m forget \
  --tag important --group-by host --keep-hourly 12 --keep-daily 7 --keep-weekly 4 --keep-monthly 6
/home/lumen/.local/bin/restic -r /home/lumen/backups/local --retry-lock 50m prune
```
(repeat against `/data/lumen/backups` for parity — that repo isn't under
pressure but a retention-policy split between the two mirrors would be its own
future footgun).

**Step 3 — verify the actual df number after 2a/2b**, not just the probe's
edge-clear (see Verify Command). If still >=92% after both, the next lever is
checking `vgs`/`pvs` for unallocated space in `ubuntu-vg` to `lvextend` the root
LV — deferred out of this plan since it needs the quantify step's numbers first
and is a different risk class (LVM online resize) than cleanup.

## Rollback Command

- Docker prune (2a) is not reversible in the sense of restoring deleted image
  layers, but is safe-by-construction: it only removes layers/containers with
  no live reference, so "rollback" is simply re-pulling/rebuilding an image if
  something unexpectedly needed a cached layer (`docker compose pull` / rebuild
  for whichever service, if any, breaks). Disable the new timer if it causes
  problems: `sudo systemctl disable --now lumen-docker-prune.timer`.
- Retention edit (2b): revert the `backup-prune.sh` line back to
  `--keep-hourly 24 --keep-daily 7 --keep-weekly 4 --keep-monthly 6` (git diff
  will show the one-line change; `git checkout -- backup-prune.sh` if tracked,
  otherwise restore from the `.bak` this apply phase should take before editing).
  The `forget` calls only drop snapshot *references* already outside the new
  retention window (older, redundant-with-other-kept-snapshots data) — they do
  not touch source data, and `--keep-hourly 12` still retains half a day of
  hourly granularity, so nothing already backed up becomes unrecoverable, just
  fewer historical points. Once `prune` physically removes now-unreferenced
  pack files, that specific space reclaim is not undoable — mitigated by
  `/data/lumen/backups` and Thoth offsite still holding the exact same history
  until *they're* separately pruned (not touched by this plan).

## Risk Assessment

- **Docker prune**: low risk if step 1's numbers confirm it's dangling
  data — `--volumes=false` is the standard safe form. Blast radius if wrong:
  a currently-stopped-but-wanted container's filesystem changes are lost (rare
  on this fleet — services run as systemd-managed long-lived containers, not
  disposable run-once ones) or a build-cache miss slows the next `docker build`.
  Acceptable.
- **Retention tightening**: shrinks Lumen's own hourly recovery window from 24h
  to 12h for the `critical`-tagged backup set (Vaultwarden, Langfuse PG,
  pgvector, Redis DB2, agent SQLite, Minerva state, Pokemon checkpoints, etc. —
  see `backup-critical.sh`). `/data/lumen/backups` and the Thoth offsite copy
  are untouched by this plan and keep the full 24h window, so this is a
  reduction in *one of three* copies' granularity, not a loss of coverage.
  Frank should confirm 12h hourly RPO is acceptable for the local-fastest-copy
  tier before this ships — flagging explicitly rather than assuming.
- **Unquantified container storage**: the real risk in this plan is proposing
  2a before step 1's numbers exist. If `docker system df -v` shows the gap is
  NOT container storage (e.g., it's actually a deleted-but-still-open file held
  by a live process, a classic df-vs-du mismatch), 2a will reclaim little and
  the plan needs a different step 2. This is why step 1 gates 2a/2b sizing —
  apply phase should not skip straight to pruning without reading the numbers.
- **Not attempted / explicitly out of scope this plan**: LVM extension
  (`lvextend`) — higher-risk class (online filesystem resize), and this
  session couldn't even read `vgs`/`pvs` to know if there's unallocated PV
  space to extend into. Left for a follow-up if 2a+2b don't clear enough
  headroom.
