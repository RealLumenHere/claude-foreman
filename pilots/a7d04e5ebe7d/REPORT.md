## Treatment (measured)

Arm B: CMT-lite — per index row, precompute a trace vector (centroid of that
row's own top-3 nearest neighbours in the 605-row index); rerank the top-5 hop-1
candidates by `0.7*cosine(query,candidate) + 0.3*cosine(query,trace(candidate))`.
This is the smallest construction that tests the proposal's mechanism (a second
hop through cached, complementary neighbourhood information reshaping the
ranking) without standing up a new service, a new pgvector collection, or a
systemd unit, none of which are justified before the mechanism itself is shown
to move the metric.

| field | value |
|---|---|
| R@1 | 0.90 (45/50) — identical to baseline |
| trace precompute time (605x605 pairwise, one-time) | 19.6 s |
| scoring time (50 queries, both arms) | 2.7 s |

## Why this reads as a real negative, not an underpowered pilot

The trace mechanism is not silently failing to activate — `alpha=0.7` means the
trace score does influence the combined rank, and the hop-1 top-5 window is wide
enough to admit reranking. It never wins because on this corpus the direct
query-candidate cosine is already decisive: the top-1 candidate's margin over
the rest of the top-5 is large enough that a 30%-weighted neighbourhood-centroid
term cannot flip the order, and where the baseline is wrong, the true parent is
apparently not in the top-5 hop-1 set at all (a rerank of the wrong candidate set
cannot recover it). Multi-hop trace reranking would need either a much higher
trace weight (untested here, and not what the proposal specifies) or a mechanism
that expands the candidate set itself, not just reorders it — a different,
larger build than "the smallest thing that tests the hypothesis."

## Scope this pilot did NOT cover

- The proposal's actual target use case is the intel/scout multi-hop pipelines,
  not proposal dedup. This pilot tested the general mechanism (does a
  neighbourhood-trace hop-2 rerank move R@1) on the only labeled retrieval set
  Lumen has. A gap on intel/scout's own query distribution is not ruled out, but
  building a labeled multi-hop dataset for that pipeline is exactly the missing
  eval-harness work the original defer named, and is L-effort on its own — out of
  scope for a 90-minute pilot budget.
- Only one (alpha, top-K, top-N-trace) configuration was tested. A wider or
  differently-weighted trace was not swept; this reports a negative for the
  configuration specified as the smallest testable build, not for every possible
  hyperparameterization of CMT.

## What would change this verdict

A labeled retrieval set drawn from the actual intel/scout multi-hop pipelines
(the proposal's real target), or evidence that the hop-1 candidate set itself
needs expansion rather than reordering — either would justify a second, larger
pilot. Neither exists today.
