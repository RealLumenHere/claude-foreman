## What was measured

Hypothesis (pre-registered in `CARD.md` before any scored call, since the card
was generated by `minerva_defer_review` with blank Hypothesis/Metric/Sample/
Baseline/Treatment sections — same situation as pilots 0eed2f5bdb92,
7c516dfb1a14, and 7187e39f4cbf): a minimal personalization-eval harness
(persona/preference facts injected vs. not, scored by a rubric) produces a
discriminating signal — treatment mean score >= 1.5x baseline mean score on a
fixed 8-task sample.

- **Baseline** (`run_pilot.py:79-97` arm=`baseline`): `gemma4-e4b-local`
  answers each task's query with only `"You are a helpful assistant."` as
  system prompt — no persona/memory context, matching today's cold-request
  default.
- **Treatment** (`run_pilot.py:79-97` arm=`treatment`): the same model, same
  query, with the task's persona/preference fact string injected into the
  system prompt (`run_pilot.py:69-71`) — the smallest stand-in for what
  `lumen-persona-engine`'s `lp_*.txt` prompts plus `lumen-convo-learn`'s
  extracted memory would supply.
- Both arms scored by the same keyword/format rubric (`run_pilot.py:32-49`
  `score()`) against the same fixed sample (`sample.json`, sha256
  `e7f188635798726827af594e7e2d60c49ae338eb397b10cfef9d7b34c23eed7a`, 8 tasks,
  `build_sample.py`).

## Results (`results_baseline.json`, `results_treatment.json`)

| arm | mean score (0-1) | total latency (8 calls) |
|---|---|---|
| baseline (no context)   | 0.3021 | 116.7s |
| treatment (facts injected) | 0.8187 | 110.2s |

Win condition (fixed before the run): treatment mean >= 1.5 * baseline mean,
i.e. >= 0.4531. **Met.** Treatment scored 0.8187, a **2.71x** improvement
over baseline (+51.7 points), clearing the pre-registered bar by a wide
margin. Per-task detail in the two JSON files; 6 of 8 tasks improved,
1 was flat-high (task 4, both arms near max on a short factual ask), and
1 regressed (task 5, "explain variables to a beginner" — the keyword rubric
rewards phrases like "simple"/"beginner" that the baseline response also used
incidentally, a rubric-precision limitation, not a personalization failure —
see Scope below).

## Scope this pilot did NOT cover

- **No live `lumen-persona-engine` / `lumen-convo-learn` integration**: their
  service code is not in this worktree (foreman is the ops/planning repo; the
  personalization services run elsewhere on the fleet). The treatment arm
  injects a fact string directly, standing in for what those services would
  produce — this measures whether *having* personalization context helps,
  not the cost, latency, or failure mode of *fetching* it from the real
  services.
- **No paper task set**: the source (classified_intel
  `f28bb9e611091397100df50ffb8d6be4`, "Benchmarking the Personalization
  Capabilities of Large Language Models", arXiv, no URL captured at intake)
  could not be fetched — this headless build-worker session had no
  WebSearch/WebFetch permission granted, and no URL was stored on ingest. The
  8-task sample is a hand-authored proxy covering the same general shape
  (preference recall, persona-adherence, prior-context memory) described in
  the paper's own classified-intel summary, not the paper's actual
  benchmark. Any future harness building on this pilot should retry pulling
  the paper (a plain desk-research/reading task, not a pilot) before scaling
  the sample.
- **Rubric is keyword/format matching, not a judge model**: cheap and fast,
  but the one regression above shows it can misfire on paraphrase. A
  production harness would want an LLM-judge or human-graded rubric.
- **Single model, single run**: `gemma4-e4b-local` only, no repeats, no
  variance estimate. The 2.71x gap is far larger than plausible noise from a
  single low-temperature-ish generation, but this is not a statistically
  powered study.

## Recommendation

Measured: on a fixed 8-task proxy personalization sample, injecting
persona/preference facts into the system prompt (treatment) raised mean
rubric score from 0.3021 (baseline, no context) to 0.8187 — a 2.71x
improvement, clearing the pre-registered >=1.5x win condition. The harness
and rubric built here (`build_sample.py`, `run_pilot.py`) do discriminate
personalized from generic responses on a real model over the real LiteLLM
gateway, which is the empirical question this pilot existed to answer: can a
lightweight benchmark-runner produce a meaningful personalization signal at
all. Yes.

Not ADOPT, because two substantial gaps remain exactly where the original
defer reason said they would: (1) this pilot did not integrate
`lumen-persona-engine` / `lumen-convo-learn` — it simulated their output as a
fact string, so there is no data on real fetch latency, staleness, or failure
modes of the actual multi-service pipeline; (2) the sample is a hand-authored
proxy, not the source paper's benchmark, because the paper was unreachable
from this session. Wiring either gap closed is real remaining effort that a
pilot budget (90 min, no live-service access) cannot retire.

Recommend WATCH: keep `build_sample.py` / `run_pilot.py` as the seed for
Lumen's eval harness (the mechanism works), but before a build (a) fetch the
actual paper and replace the proxy sample with its real tasks, and (b) run a
follow-up pilot that calls the live `lumen-persona-engine` +
`lumen-convo-learn` pipeline instead of an injected fact string, to measure
real latency and failure behavior, not just the personalization-signal
question this pilot answered.
