Ticket: wq#1683. Card: `CARD.md` (this directory). Ran on the wq1683 build-worker

## What was measured

Hypothesis (pre-registered in `CARD.md` before any run, since the card was
generated by `minerva_defer_review` with blank Hypothesis/Metric/Sample/
Baseline/Treatment sections — same situation as pilots 0eed2f5bdb92 and
7c516dfb1a14): a minimal token-economy allocation mechanism (a shared budget
spent by a global value/cost price signal across agents) captures more total
task value than today's purely task-driven routing (a fixed per-agent
sub-budget spent in arrival order, no cross-agent signaling), under the same
fixed shared token budget and task pool, by at least 15%.

Both arms ran against the same fixed 60-task synthetic sample
(`sample.json`, seed 1683, sha256
`031c565c05e578476cd55e6c11adda48a8c23a84c71861202a8e649eca3bf9ef`), same
shared token budget (100), same 3 agents (cerebras, mistral, openrouter) with
tasks round-robin pre-assigned as each agent's "home" task.

- **Baseline** (`run_pilot.py:22-38` `run_baseline`): the proposal's own
  "current state" — no token-based signaling or budget allocation. The
  shared budget is split evenly (33.3 tokens/agent) up front; each agent
  completes only its own home tasks, in fixed arrival (task id) order, until
  its own sub-budget runs out. No agent sees another agent's tasks or their
  value/cost ratio.
- **Treatment** (`run_pilot.py:41-48` `run_treatment`): the smallest
  mechanism matching "agents query the economy service for budget
  constraints before selecting research actions" — one shared token pool,
  every task from every agent ranked by value/cost ratio, tokens spent
  top-ratio-first regardless of task owner. No systemd service, timer, or
  LLM-simulated dynamics were built; those are infrastructure around the
  mechanism, not the coordination mechanism itself, which is what the
  hypothesis is about.

## Results (`results_baseline.json`, `results_treatment.json`)

| arm | tasks completed | cost spent / 100 | value captured | % of fractional optimum (214.41) |
|---|---|---|---|---|
| baseline (no economy) | 19 | 98 | 171.412 | 79.95% |
| treatment (economy)   | 16 | 100 | 212.837 | 99.27% |

Win condition (fixed before the run): economy-arm value captured >= 1.15 *
no-economy-arm value captured, i.e. >= 197.12. **Met.** Treatment captured
212.837, a **1.242x** improvement over baseline (+24.2%), clearing the
pre-registered 15% bar by a wide margin. The economy arm also completed
fewer tasks (16 vs 19) while capturing more value and spending its full
budget (100 vs 98) — it is trading task *count* for task *value density*,
which is the intended effect of a price signal.

## Scope this pilot did NOT cover

- **No real fleet data**: the sample is synthetic (see Fixed sample in
  `CARD.md`) because no Lumen telemetry of "agent picks task A over task B
  under a budget constraint" exists yet — that signaling is precisely what
  the proposal would introduce. The *relative* result (global ratio-ranked
  allocation beats fixed-order local greedy under a shared scarce resource)
  is a general resource-allocation property, not an artifact of the
  synthetic cost/value distribution, but the *magnitude* (24.2%) is specific
  to this sample's cost/value noise and would shift with real task
  distributions.
- **No systemd service, timer, or LLM-simulated economic dynamics**: the
  proposal calls for `lumen-agent-economy.service`, a JSON state file at
  `/data/lumen/economy/state.json`, and `lumen-lfm2-1b` simulating dynamics
  hourly. None of that was built or is needed to test the core hypothesis
  (does global price-signal allocation beat local fixed-order allocation);
  building it is real remaining effort and risk (a new standing service,
  new state file, new failure mode) that this pilot is silent on.
- **No coordination overhead was modeled**: the treatment arm's ranking is
  computed instantaneously and centrally in this simulation. A real
  `lumen-agent-economy` service adds latency (each agent must query it
  before acting), a new dependency all fleet researchers share (a single
  point of failure/bottleneck), and staleness risk (prices computed hourly
  by an LLM, per the proposal, lag actual task availability). None of that
  cost is reflected in the 24.2% figure above.
- **Evaluator/planner duo** named in the proposal's rollout scope was not
  modeled at all; only the 3 fleet researchers were simulated.

## RECOMMENDATION: WATCH

Measured: under a fixed shared token budget (100) and a fixed 60-task
synthetic sample (seed 1683), a minimal global price-signal allocation
mechanism (treatment) captured 212.837 value units (99.27% of the
fractional-knapsack optimum) vs. 171.412 (79.95% of optimum) for today's
fixed-order per-agent allocation (baseline) — a 1.242x improvement, clearing
the pre-registered >=1.15x win condition. The core coordination *mechanism*
(global ratio-based allocation beats local fixed-order allocation under a
shared scarce budget) is a real, measured, and unsurprising result — it is a
restatement of why greedy-by-ratio beats greedy-by-arrival-order under a
knapsack constraint, applied to agent task selection.

Not ADOPT, because the proposal is a standing service
(`lumen-agent-economy.service`, a new state file, hourly LLM-simulated
dynamics), and this pilot measured only the allocation math, not the
service: no data on query latency added to every agent's action-selection
path, no data on the failure mode of a shared allocator agents now depend
on, no data on price staleness from hourly (vs. real-time) recomputation,
and no fleet data confirming real task cost/value distributions look like
this synthetic sample. Those are exactly the risks a lightweight pilot
cannot retire, and per the card's own scope limit, an ADOPT here would go
straight to minerva-factory PLAN and get built as a standing service — that
commitment isn't justified by an allocation-math result alone.

Recommend WATCH: the mechanism is worth carrying forward as a design
constraint (any future coordination layer should rank by value/cost, not
route by fixed per-agent order), but before a build, a follow-up pilot
should (a) pull a real extract of fleet-researcher task cost/value if one
can be instrumented, and (b) measure the actual query latency and failure
behavior of a minimal `lumen-agent-economy` service prototype, not just the
allocation algorithm in isolation.
